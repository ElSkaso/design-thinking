# Define Reference

Use this reference to transform research into a focused product problem.

## Problem Framing

A strong problem frame is:

- Human-centered
- Grounded in research
- Broad enough for creative solution exploration
- Narrow enough to guide design
- Clear about user, context, barrier, cause, and consequence

Separate:

- Problem: what blocks the user
- Need: what the user must accomplish
- Insight: why the problem matters
- Constraint: what limits possible solutions
- Outcome: what success would change

## 5W And H Check

Answer these before finalizing a problem statement:

- Who experiences the problem?
- What pain point or barrier are they facing?
- Where does the problem occur?
- When does it occur?
- Why is the problem important?
- How do users currently try to reach their goal?

## Problem Statement Templates

User point-of-view format:

```text
I am [PERSONA], trying to [GOAL], but [BARRIER], because [CAUSE], which makes me feel [EMOTIONAL_REACTION].
```

Research-derived format:

```text
[USER_OR_PERSONA] is a [USER_CHARACTERISTIC] who needs [NEED] because [INSIGHT].
```

Review:

- Does it describe a user need rather than a product feature?
- Does it avoid prescribing the solution?
- Can a design team act on it?
- Can success be evaluated later?

## User Needs Statement

Use when the team needs a concise design target.

```text
[USER_OR_PERSONA] needs a way to [USER_NEED] because [INSIGHT_OR_CONTEXT].
```

Include a success benchmark when possible:

```text
Success means [OBSERVABLE_CHANGE_OR_MEASURE].
```

## Hypothesis Statements

Hypotheses connect an intervention to an expected user or business outcome.

If/then format:

```text
If we [DESIGN_ACTION], then [USER_OR_SEGMENT] will [EXPECTED_BEHAVIOR_OR_OUTCOME], because [EVIDENCE_OR_REASON].
```

We believe format:

```text
We believe [SOLUTION_DIRECTION] for [USER_OR_SEGMENT] will [OUTCOME]. We will know this is true when [MEASURE_OR_SIGNAL].
```

## Problem/Hypothesis Pairs

Pair each problem statement with one or more testable hypotheses.

Quality check:

- The problem is evidence-backed.
- The hypothesis is testable.
- The expected outcome is observable.
- The pair does not assume one fixed UI solution too early.

## Value Proposition

A value proposition explains why the solution is useful and different.

Answer:

- Who is this for?
- What problem does it solve?
- What outcome does it create?
- Why is this better than the current workaround or alternatives?
- What evidence supports the promise?

Template:

```text
For [TARGET_USER] who [USER_CONTEXT], [PRODUCT_OR_CONCEPT] helps them [PRIMARY_OUTCOME] by [CORE_VALUE_MECHANISM], unlike [ALTERNATIVE_OR_WORKAROUND].
```

## Human Factors

Use these ideas when reviewing a problem or solution:

- Mental models: users bring expectations from prior experiences.
- Feedback loops: users need to understand whether an action worked.
- Hick's Law: too many choices can slow decisions.
- Serial position effect: users tend to remember first and last items.
- Isolation effect: visually distinct items attract attention.

Apply human factors as design rationale, not decoration.

## Define Audit

- The problem is about user need, not a predetermined feature.
- Claims trace to empathize artifacts or research.
- Hypotheses are testable.
- Value proposition is specific to a user segment.
- Human factors are used to clarify behavior and decisions.
